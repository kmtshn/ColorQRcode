# 6ColorQR

> 6色カラーコードの生成とカメラでのリアルタイム読み取りができる、オフライン動作対応のPWAアプリ

スマートフォンのブラウザ（Safari / Chrome）だけで動作し、サーバーや外部ライブラリ不要。
オフィスの蛍光灯下を想定した、シンプルで堅牢な6色カラーコードシステムです。

---

## ✨ 特長

- 📱 **PWA対応** — ホーム画面に追加、オフラインでも起動可能
- 🎨 **6色エンコード** — 白黒QRの約2倍の情報密度（1セル ≈ 2.58 bit）
- 📷 **自動位置補正** — 粗探索→細探索の2段階でガイド枠の多少のズレを自動補正
- 🔒 **チェックサム** — XORチェックサムで誤読をほぼ完全に排除（1/256以下）
- 💡 **レフ板モード** — スキャン中は背景を真っ白にしてスマホ画面を照明代わりに
- 🪶 **超軽量** — 3ファイル合計 約42KB、外部ライブラリゼロ（Vanilla JS）
- 🛠 **デバッグ表示** — 検出セルをリアルタイム可視化（DBGボタン）

## 🚀 使い方

### ローカルで動かす

```bash
python3 -m http.server 8080
# → http://localhost:8080 をブラウザで開く
```

> ⚠️ カメラAPI (`getUserMedia`) を使うため、**HTTPSまたはlocalhost**が必要です。
> スマホ実機テストはGitHub Pages / Cloudflare Pages / Netlify 等にデプロイしてください。

### 読み取りのコツ 💡

1. **明るい場所**で撮る（蛍光灯下推奨、影を避ける）
2. コードを**画面緑枠の中央**に収める（自動補正で多少ズレてもOK）
3. **5〜15cm**離してピントを合わせる
4. 反射する印刷面（光沢紙）は角度をずらして反射を避ける
5. 印刷時は**5cm角以上**を推奨（小さすぎるとセル境界がにじむ）

## 🎨 6色カラーコード仕様

### 色の割り当て

| 値 | 色 | RGB | HEX | HSV (近似) |
|:-:|:-:|:-:|:-:|:-:|
| 0 | ⬜ 白 | (255, 255, 255) | `#FFFFFF` | V=1.00, S=0.00 |
| 1 | ⬛ 黒 | (0, 0, 0)       | `#000000` | V=0.00, S=0.00 |
| 2 | 🟥 赤 | (225, 29, 72)   | `#E11D48` | H=347°, S=0.87, V=0.88 |
| 3 | 🟨 黄 | (250, 204, 21)  | `#FACC15` | H=48°,  S=0.92, V=0.98 |
| 4 | 🟩 緑 | (22, 163, 74)   | `#16A34A` | H=142°, S=0.87, V=0.64 |
| 5 | 🟦 青 | (37, 99, 235)   | `#2563EB` | H=221°, S=0.84, V=0.92 |

### コード構造

```
16 × 16 = 256セル

┌──────────────────┐
│⬛⬛………………⬜⬜│  ← 4隅に 2×2 ファインダー
│⬛⬛………………⬜⬜│
│ │              │
│ │  データ領域  │
│ │              │
│🟥🟥…………🟦🟦│
│🟥🟥…………🟦🟦│
└──────────────────┘
```

| ファインダー (2×2) | 色 | 役割 |
|:-:|:-:|:-:|
| 左上 | ⬛ 黒 | 明度キャリブレーション（暗側）+ 向き判定 |
| 右上 | ⬜ 白 | 明度キャリブレーション（明側）+ 向き判定 |
| 左下 | 🟥 赤 | 色相基準 + 向き判定 |
| 右下 | 🟦 青 | 色相基準 + 向き判定 |

各ファインダーは2×2の同色ブロックなので、**16セルすべてが一致する位置を自動探索**できます（粗→細の2段階）。

### データレイアウト

```
全256セル = 16(ファインダー) + 7(ヘッダー) + 233(データ)

ヘッダー (7セル):
  ├─ 長さ (3桁 6進数) → 0〜215の値
  └─ XORチェックサム (4桁 6進数) → 0〜255のバイト

データ (最大232セル):
  └─ 1バイト = 4セル
  → 最大 58 バイト（安全マージン込みで 48バイト まで使用）
```

### エンコードロジック

1. 入力文字列を **UTF-8 バイト配列** に変換
2. 全バイトの **XORチェックサム** を計算（誤読検出用、長さも含めて撹拌）
3. ヘッダー(3+4セル) + 各バイト(4セル) をストリームに展開
4. ファインダー以外のセルに走査順（左→右, 上→下）で書き込み
5. **最大格納容量: 48バイト**

```
1バイト = log₂(256) = 8 bit
4セル   = log₂(6⁴) ≈ 10.34 bit
→ 効率: 8 / 10.34 ≈ 77% のbit利用率
→ 同サイズの白黒QRより約2倍の容量密度
```

### デコードロジック（HSV判定 + 自動補正 + チェックサム）

```
1. ガイド枠領域を初期推定矩形として取得
2. 粗探索 (125点): 中心±12%・スケール 0.80〜1.20
   各候補で 16×16 サンプリング → ファインダー一致セル数を集計
3. 細探索 (125点): 上位候補の周辺で ±4%・スケール 0.96〜1.04 を再探索
4. 16/16 完全一致または最大スコアの矩形を確定
5. 各セル中央付近の9点をサンプリング → 多数決で色決定
6. HSV判定:
   - 4隅から白/黒のV値を取得 → 動的キャリブレーション
   - V≤0.22 → 黒（暗部は色相を信用しない）
   - 正規化明度・彩度・色相角の最近傍判定で白/黒/赤/黄/緑/青を決定
7. ヘッダーから長さ＋チェックサムを抽出
8. データ部のXORチェックサムが一致しなければ「誤読」として破棄
9. UTF-8として復元（fatal: trueで不正バイトもエラー化）
```

**ファインダー検出だけでは誤読の可能性があるため、必ずチェックサムも確認します。** 連続フレームでチェックサム合致したものだけが採用されるため、誤読確率は実質的にゼロです。

## 🔬 技術詳細

### 使用技術

- **HTML5 Canvas API** — 描画 / ピクセル取得
- **MediaDevices API** — `getUserMedia` でカメラ映像取得（連続オートフォーカス指定）
- **TextEncoder / TextDecoder** — UTF-8の変換（`fatal: true` で不正バイト検出）
- **Service Worker API** — オフラインキャッシュ
- **Web App Manifest** — PWA設定
- **Clipboard API** / **Vibration API** — UX強化

外部ライブラリ・フレームワークは **一切使用していません**。

### スキャンの仕組み

```
カメラ映像 (1280×1280目標, 連続AF)
   ↓ 200msごと（5 fps）
ガイド枠領域を計算 (object-fit: cover を考慮)
   ↓
[粗探索] 5×5×5 = 125点の (x, y, scale) を試行
   各点で 16×16 サンプリング → ファインダースコア計算
   ↓
[細探索] best 周辺で 5×5×5 = 125点再試行
   ↓
最良グリッドで decode + チェックサム検証
   ↓
成功 → 結果表示 + バイブ
失敗 → 次フレームへ
```

## 📐 容量設計の根拠

```
全セル数:           16 × 16             = 256
ファインダー:       4 × 2×2             = 16
ヘッダー:           3(長さ) + 4(CRC)    = 7
データ可用セル:     256 - 16 - 7        = 233
1バイトあたり:      4セル
最大バイト数:       233 / 4 = 58.25 → 58 → 48 (安全マージン)
```
